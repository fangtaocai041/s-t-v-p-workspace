# ocr-solution-audit — OCR 方案全景审计

## 背景
当项目中存在多个 OCR 脚本时，需要从精度、速度、成本、安全、可维护性五个维度做横向对比，找到最优方案或合并重复代码。

## 审计五维框架

### 1️⃣ 引擎分类
将所有 OCR 脚本按引擎分组：
- **本地 Tesseract**（tesseract.js）
- **云端通用 OCR API**（百度 OCR）
- **AI 视觉大模型**（Gemini / OpenAI / Claude）
- **专用 OCR 平台**（PaddleOCR / 其他）

### 2️⃣ 每个脚本的检查清单
- [ ] OCR 引擎/模型名称
- [ ] API 端点（若有）
- [ ] 图片来源（CLI 参数 / 硬编码路径）
- [ ] 图片预处理（resize/灰度/切割/压缩）
- [ ] 有无重试/降级/错误处理
- [ ] 输出格式（纯文本 / JSON / Markdown 表格）
- [ ] **硬编码敏感信息**（API Key / Token / 本地路径含用户名）
- [ ] 网络依赖（需代理？直连？离线？）

### 3️⃣ 对比表格模板
| 维度 | 脚本A | 脚本B | ... |
|------|-------|-------|-----|
| OCR 引擎 | | |
| 精度(1-5) | | |
| 速度 | | |
| 网络依赖 | | |
| 每次成本 | | |
| 安全评分 | | |
| 可维护性 | | |

### 4️⃣ 推荐结论
- **最推荐**：综合最佳
- **快速方案**：最快能跑起来的
- **高精度方案**：精度第一
- **离线方案**：无网络环境
- **安全风险**：⚠️ 列出所有含硬编码密钥的脚本
